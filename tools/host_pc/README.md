# Y75 上位机（RS485 · Python）

对接 **Y75 六维力传感器** 的 RS485 上位机。协议是自定义帧：

```
AA 55 [CMD] [PAYLOAD...] 0D 0A
```

纯 Python 标准库（tkinter + ctypes + zipfile），**零第三方依赖**，
可以直接跑源码，也可以打包成单个 `.exe` 免安装使用。

---

## 快速开始

### 直接用 exe（推荐）

双击 `dist\Y75_Host.exe`（自己重新打包见下文）。

1. 插好 USB-RS485 转换器 → 左上「刷新」→ 选中串口（默认 460800）
2. 点「连接」→「读取设备信息」
3. 点「开始连续」看波形；「开始保存数据」导出 Excel

### 跑源码

```bat
python y75_app.py                      :: 界面
python y75_app.py --port COM28         :: 直接指定串口
python y75_app.py --autoconnect        :: 连上后自动开始连续采集（配合 --sim / --port）
python y75_app.py --selftest           :: 只建界面，验证打包后的 exe 能起来
```

### 没有硬件也能玩（设备模拟器）

```bat
python y75_simulator.py --port 15020        :: 窗口 1：模拟设备
python y75_app.py --sim                     :: 窗口 2：连它
python y75_app.py --sim --autoconnect       :: 连上后自动开始推流
```

模拟器走 TCP（默认 `127.0.0.1:15020`），**协议字节流与真机完全一致**，
只是传输层换成了 socket，方便在没有串口线的机器上开发与回归。

想让模拟器更像真机（复现 USB 串口驱动的「成批上报」），加 `--burst-ms`：

```bat
python y75_simulator.py --port 15020 --burst-ms 16     :: 每 16ms 攒一批再发，和 CH340/FTDI 一样
python y75_simulator.py --port 15020 --short-frames 5  :: 每 5 帧插一个畸形帧 AA 55 02 0D 0A
```

## 命令速查（协议层）

| 命令码 | 作用 | 请求 | 设备回复 |
|---:|:--|:--|:--|
| `0x01` | 停止连续发送 | `AA 55 01 0D 0A` | `AA 55 81 0D 0A` |
| `0x02` | 开始连续发送（**本上位机已不使用**） | `AA 55 02 0D 0A` | `AA 55 82 0D 0A`，随后按频率推流 |
| `0x03` | 单次采集 | `AA 55 03 0D 0A` | **直接回一帧数据**（无 ACK） |

> **本版「开始连续」= 每 50 ms 发一条 0x03 轮询**（`y75_protocol.POLL_INTERVAL`），
> 设备逐条回一帧数据，点「停止」即停发轮询。固件的 0x02 推流仍保留
> （老版本上位机 / 自动启动标志会用到），但本上位机不再发送它。
> 数据密度因此是 20 点/秒：5s 时间窗一屏约 100 点，波形比推流模式「稀」是
> 预期行为；横轴比例/滚动全部按帧计数推算，与推流模式一样不抖。
| `0x04` | 设置波特率 | `AA 55 04 [码] 0D 0A` | `AA 55 84 0D 0A`，**先回 ACK 再换档** |
| `0x05` | 查序列号 | `AA 55 05 0D 0A` | **裸 ASCII**（无帧头帧尾） |
| `0x06` | 查固件版本 | `AA 55 06 0D 0A` | `AA 55 86 [3B] 0D 0A` |
| `0x07` | 查运行状态 | `AA 55 07 0D 0A` | `AA 55 87 [8B] 0D 0A` |
| `0x08` | 设置输出频率 | `AA 55 08 [0\|1] 0D 0A` | `AA 55 88 0D 0A`（0=500Hz 1=1000Hz） |
| `0x0A` | **写序列号** | `AA 55 0A [ASCII 1..15] 0D 0A` | `AA 55 8A [状态] 0D 0A`：`00`=已存、`01`=长度/字符非法、`02`=EEPROM 写失败。**固件 V1.7.4 起**；存 EEPROM `0xB0..0xBF`，上电读回，写完 `0x05` 能读到新值 |
| `0x0E` | 查当前单位 | `AA 55 0E 0D 0A` | `AA 55 8E [01=kg\|00=N] 0D 0A`（读设备信息时自动查） |
| `0x0F` | 心跳灯闪烁 | `AA 55 0F 0D 0A` | `AA 55 8F 0D 0A`，PA12 以 1Hz 闪烁，发 `0x01` 熄灭 |
| `0x20` | 上传矩阵一行 | `AA 55 20 [行 0..5] [6×f32 **大端**] 0D 0A` | `AA 55 A[行] 0D 0A`（行号带在命令码里） |
| `0x30` | 执行置零 | `AA 55 30 0D 0A` | `AA 55 B0 0D 0A`（**异步**，采 20 点） |
| `0x31` | HEX 输出模式 | `AA 55 31 0D 0A` | `AA 55 B1 0D 0A` |
| `0x32` | ASC 输出模式 | `AA 55 32 0D 0A` | `AA 55 B2 0D 0A` |
| `0x33` / `0x35` | 单位 kg / N | `AA 55 33 0D 0A` | `AA 55 B3 / B5 0D 0A`（写 EEPROM） |
| `0x34` | 单位 mV | `AA 55 34 0D 0A` | `AA 55 B4 0D 0A`（不保存） |
| `0x36` | 取消置零 | `AA 55 36 0D 0A` | `AA 55 B6 0D 0A` |
| `0x37` | 查矩阵 | `AA 55 37 0D 0A` | **6 行裸 ASCII** `matrixN: a, b, …` |
| `0x38` | 读矩阵一行（二进制） | `AA 55 38 [行 1..6] 0D 0A` | `AA 55 B8 [行] [6×f32 **大端**] 0D 0A`；**「读取设备矩阵」走这条**，逐行读 6 次。行号 1=第一行（与 0x37 的 matrix1~6 对齐），注意 0x20 写入的行号是 0~5 |

数据帧：`AA 55 [02|03] [6 × float32 小端] 0D 0A`，共 **29 字节**。

> **两套字节序别混**：推流/单次数据帧（`0x02`/`0x03`）是**小端**（`1.0 → 00 00 80 3F`），
> 矩阵行（`0x20`/`0x38`）是**大端**（`1.0 → 3F 80 00 00`）。界面上那个「浮点字节序」
> 下拉框只管前者，矩阵固定走大端（`ByteOrder.MATRIX_ORDER`）。
ASC(调试) 模式下数据帧变成**裸 28 字节**：`[6 × float32 小端] + 00 00 80 7F`（+Inf 哨兵）。

状态字（0x07 的 8 字节，小端）：`send_mode / data_format / freq_mode / debug_mode / status_flags(2) / comm_error_cnt(2)`；
`status_flags` BIT0=自动启动、BIT1=运行中。

## 序列号（「序列号」页签 · 0x0A 写 / 0x05 读）

「报文日志」右边那个页签。读是 `0x05`（裸 ASCII），写是 `0x0A`（**固件 V1.7.4 起**）。

- 规则：**1~15 位**，只允许字母、数字和 `- _ .`（固件 `g_config.sn[16]` 的长度决定的）。
  输入框边打边校验：超长/含空格会标红并禁用「写入设备」，**上位机就不发帧**，
  不用等设备打回来。
- 写入前弹确认框（写 EEPROM 不可撤销）；写完**自动用 0x05 回读**，只有读回来
  和写下去的一致才报成功，否则报「回读不一致」。
- 设备用**状态字节**回复（不是裸 ACK），所以能分清三件事：
  `8A 00` 已存 / `8A 01` 内容非法 / `8A 02` EEPROM 写失败；
  如果**压根没回复**（超时），基本就是固件版本低于 V1.7.4、没有这条命令。
  页签里会按「读取设备信息」拿到的版本号提前提示支不支持。
- 固件侧存 **AT24C04 的 `0xB0..0xBF`**（正好一页，16 字节，`0xFF` 填充），
  上电 `main()` 读回 `g_config.sn` 并校验字符/长度，空白或损坏就退回编译期默认值。

> EEPROM 地址占用（AT24C04，512 字节）：`0x00..0x77` 矩阵第 1~5 行、`0x78..0x7B`
> 波特率、`0x7C` 单位、`0x80..0x97` 矩阵第 6 行、`0x98..0xAF` 零点偏置、
> **`0xB0..0xBF` 序列号**（`0xC0` 之后空着，留扩展）。

## 真机联调注意事项（读固件源码得到的结论）

> 协议实现见 `Core/Src/rs485_cmd.c` / `Core/Src/rs485.c`，**以上位机源码里的结论为准**。

1. **默认 460800 8N1**。设备把波特率写进 EEPROM，改过之后掉电不会恢复默认；
   连不上时先试试其它档位（模拟器的 `--silent` 可复现「完全不回」的现场）。
2. **改波特率先回 ACK 再换档**。上位机收到 `0x84` 之后才切换本机串口，界面上有确认弹窗。
3. **没有任何事务号**。响应只能靠命令码区分，所以上位机**默认不做超时自动重试**
   （「总线仲裁」面板里的「无应答重发」= 0）—— 迟到的响应会被下一个等待者错认，
   比直接报超时危险得多；只有在你明确知道这条命令幂等、且总线确实有丢帧时才调大。
4. **0x05 / 0x37 的回复没有帧头帧尾**。上位机靠「总线静默 > 120 ms」判定一条回复结束，
   同时要求整段都是可打印 ASCII（二进制 float 恰好整段可打印的概率 ~0.37^n，可忽略）。
5. **0x32 切到 ASC 后，数据帧连 AA55 都没有**，必须靠结尾的 `00 00 80 7F` 哨兵识别；
   该模式下 ACK 仍是标准帧，两种格式并存。界面上切到 ASC 会有黄色警告。
6. **拆帧优先按已知长度**，长度对不上才退回「向后找 `0D 0A`」——
   这样即使浮点载荷里恰好出现 `AA 55` / `0D 0A` 也不会切错。
7. **USB-RS485 转换器的方向控制**：固件从不手动拉方向脚，说明板上收发器是自动方向的；
   上位机默认拉高 DTR/RTS（多数转换器靠它们取电/使能），个别用 RTS 做方向控制的
   转换器需要关掉这个勾选。
8. **推流是设备主动发的**（500/1000 Hz，非主从问答），这是协议的非标准扩展；
   报文日志默认**不记**推流帧，否则 500 Hz 会刷屏卡死界面（可勾选每 50 帧记一条）。

## 总线仲裁：为什么点「停止」要等一下才发（针对 MAX13487）

**现场**：用 MAX13487（自动方向收发器，板上没有 DE 脚）时，逻辑分析仪上能抓到
485 同时收发 → 设备侧拆到垃圾帧，严重时直接进 `HardFault_Handler`。

**原因**：半双工 485 只有一个说话权。设备在推流时总线几乎一直被它占着：

    460800 波特率下，29 字节数据帧占 29×10/460800 ≈ 0.63 ms；
    500 Hz 时帧周期 2 ms → 每帧之后只有约 1.37 ms 空隙；
    一条 8 字节命令占 0.17 ms，塞进空隙绰绰有余。

命令落在空隙里没事；落在设备**正在发的那一帧**中间，两个驱动器一起拉总线，
两边收到的都是垃圾。

**上位机的做法**（`y75_protocol.py::BusGate`，左栏「总线仲裁」面板可调）：

1. **所有出站字节都必须先过仲裁**：`_transact` / 单次采集 / 查矩阵 / 自定义报文，
   一个都绕不过去；
2. **等「当前这一帧收完」再发** —— 而且必须**踩着帧收完的那一瞬间发**：
   接收链路有延迟 d（USB 转换器的 Latency Timer、驱动缓冲都算在内），你看到
   「第 N 帧收完」时，总线上离下一帧开始只剩 `1.37ms - d`。所以规则是
   收包线程一收完整帧就 set 事件，发送方立刻被唤醒写下去（实测反应 <0.2ms），
   而不是先傻等 0.8ms 静默再发 —— 后者会把余量吃光，实测撞车率约 30%；
3. **只有数据帧（0x02/0x03）才算可靠边界**：ACK 是主循环插空发的，
   它收完的下一微秒可能正好接上推流帧，把它当信号必撞；
4. **guard**：自己刚发过命令的 2 个帧周期内不再发，别踩设备正在回的 ACK；
5. **设备没在推流时立刻发**（静默 ≥ 4 个帧周期判定），「停止之后再点单次」不受影响；
6. **看得到就显示**：等过多少次、均/最长等了多久、有没有「看不到帧边界就发」的
   情况（那说明串口驱动在攒批，把 Latency Timer 调到 1ms）。

**效果**（模拟器 `--collide` 模式实测，设备发送窗口内的命令一律丢弃）：

    关闭仲裁：12 条命令 3~8 条被丢
    开启仲裁：8 条命令 0 条被丢（写入全部落在帧收完后的 0.1~0.2 ms 内）

**给真机的提醒**：500 Hz 时余量只有 1.2ms 左右，USB 转换器的 Latency Timer
一定要调到 1ms（设备管理器 → 端口 → 高级），否则上位机看到的帧边界滞后太多，
仲裁也只能尽力而为。实在不行的兜底是「无应答重发」调到 1（仅对幂等命令）。

## 波形为什么这么画（调「柔顺度」看这里）

波形看着卡，绝大多数时候不是帧率不够，而是**抖动**。这一版专门压掉了五个来源：

| 抖动来源 | 原来的做法 | 现在的做法 |
|:--|:--|:--|
| **时间轴一跳一跳** | 右边界钉在「最新一帧的**到达时刻**」上。USB 串口驱动每 8~16ms 攒一批才交给应用层，于是波形一批一批地往前蹦 | 右边界是一个**绝对点数**的积分：每帧按平滑后的帧周期前进，只用速度微调（±35%）朝「最新点 − 目标落后量」收敛。与数据到达节奏、设备时间戳全都无关（详见下一节） |
| **没新数据就不重绘** | 每个 tick 先问「有没有新帧」，没有就跳过重绘。串口批间隔几十毫秒 → 重绘也几十毫秒一次，重绘频率被数据到达节奏拖着走 | 每 tick **照常重绘**（复用上一批样本），重绘频率只由「刷新」设置决定。实测 60ms 成批条件下 16.6 → 34.9 fps |
| **波形里一根根竖条**（串口特有，TCP 没有） | 设备时钟的「批级纠偏」是让批内每帧都加一份纠偏量：纠偏增益 = 5% × 批内帧数。串口一批 20~60 帧，增益超过 1 就振荡，纠偏量一旦超过帧周期，批内时间戳原地踏步 → 整批点画在同一个 x 上 = 竖条 | 帧间隔神圣不可侵犯：批内永远严格等间隔；对钟只在批边界挪一小步（≤半个帧周期）。实测 60ms 成批下竖条帧数 = 0 |
| **同批帧时间戳重叠** | 时间戳直接取「收到的那一刻」，一批 8 帧挤在同一个毫秒里，时间轴上这 8 个点完全叠在一起 | 推流帧的时间戳按**标称采样周期**等间隔推算（再柔性对齐本地时钟），实测间隔标准差 0.031ms、0 个重叠帧 |
| **Y 轴呼吸** | 每帧拿数据重算 min/max，量程上下抽动，波形跟着抽 | 立刻扩张（绝不裁掉尖峰）、缓慢收缩（每帧收 10%），轴基本钉住不动 |
| **曲线又稀又毛糙** | 在整段 12s 缓冲上抽稀，落在可视 5s 里的点只剩约 46%，且等间隔跳采会让曲线忽高忽低 | 先按时间窗裁到可视区间，再均匀抽稀到**约 1 点/像素**（密度提升约 2 倍） |
| **每帧重建图元** | 每帧 `delete("all")` 再建 40 多个图元 | 图元建一次，之后只 `coords()` 更新 6 条曲线；网格/坐标轴/图例只在尺寸或单位变化时重排 |

### 横轴两种模式：时间（秒）↔ 点数

波形下方工具栏的「X 轴」下拉框可以切换：

* **时间 (s)** —— 跨度选 1/2/5/10/20 秒，刻度是 `-5.0s … 0`；
* **点数** —— 跨度选 **1000 / 2000 / 5000 / 10000 / 20000 个采样点**，刻度是
  `-2000 … 0`。切过去之后工具栏会顺带显示「≈ 4.0 s @ 500 Hz」，告诉你这一屏
  折合多少秒（按实测采样间隔算，不按协议标称值）。

点数轴的意义：设备实测节拍常在 300~500Hz 之间漂，并不严格落在 500/1000 两档上。
按**点**看波形时，一个周期占几点、两帧之间隔几点是确定的，数点、对齐、估频谱
都比秒直观。

实现上两件事值得知道：

1. **相邻点严格等间距 —— 两种模式都是**。横坐标一律用采样点序号，**不拿帧时间戳
   当 x**。时间模式与点数模式的画法完全相同，区别只在刻度文字（一个把「第几个
   点」换算成秒，一个直接写点数）。
2. **换轴不换平滑机制**。两种模式共用同一个「落后最新点多少个点」的位置控制器，
   只是把「落后多少点」除以实测采样间隔换算成「落后多少秒」写刻度，所以切模式
   不会退化成「来一批蹦一下」。

**横轴为什么"只看帧计数、完全不看时间戳"**（"每次像从头重新加载"的根治）

真机上时间戳是**不可信**的，而老实现在三个地方都信了它：

| # | 老实现 | 真机上会发生什么 |
|:--|:--|:--|
| ① | 右边界 `t_end = 本地时钟 − 显示延迟`，却拿它跟 `newest`（**设备时钟推算值**）比大小、谁靠前夹谁 | 推流率常在 300~500Hz 而 `sample_dt` 按 500Hz 推算，几秒就攒出几十毫秒；协议层还有「\|now − 设备时钟\| > 0.4s 就重锚」。任一发生 → `t_end = newest` 把右边界整体往回拽 → 整条曲线猛跳一截、再花十几秒爬回去 |
| ② | 右边界 `= n_all − back`，而 `n_all` 只在**数据到货**时跳变 | USB 驱动 9.9ms 攒一批、5 帧一跳 → 没新帧的位置纹丝不动，到货那帧整批跳一次 |
| ③ | 采样周期 `dt_est` = 帧时间戳相邻间隔的**中位数**，一屏点数 `= window_sec / dt_est` | 协议层有条兜底：设备时钟跑到本机时间前面时按 `sample_dt × 0.05` 把时间戳挤压过去。连续触发 → 中位数从 2ms **塌到 0.1ms** → 一屏点数从 2500 变成 **50000** → 整条曲线被压到右边缘、再随数据一点点往左扫，就是**「点从最右边刷到左边」** |

③ 是最狠的一条，而且**只在真机出现**：TCP 模拟器节拍精确、时间戳永远规整，
`dt_est` 从来不会塌，所以每次编译时给你看的模拟波形都是正常的。

现在的做法（`WaveCanvas.draw()` 第 1b 节 + `_measure_rate()`）——横轴的
**比例**和**位置**全部只从「累计帧计数」导出：

```text
rate     ← 帧计数增量 ÷ 墙钟增量（EMA），单位 点/秒
dt_est   = 1 / rate                      # 不再从时间戳算
pos_abs  ← 每帧 + 平滑帧周期 × rate × 速度
速度      = 1 ± 35%，由 (最新点 − 目标落后量 − pos_abs) 决定
右边界    = pos_abs − 本切片首点的绝对序号
```

样本也一律**按个数**取（`want_points()`），不按时间戳切 —— 否则设备时钟一重锚，
切片长度就变，`_base` 跟着突跳。

三个性质：

* **与时间戳无关** → 时钟漂移、重锚、挤压、停止/开始，画面纹丝不动；
* **与到货节奏无关** → 数据一批一批来，画面照样匀速走；
* **位置是速度的积分** → 永不突跳，误差只体现为"略微快一点/慢一点"。

`test_gui.py` 有两节守这个。第 8 节：喂 ±60ms 抖动的时间戳点间距变异必须为 0；
连画几帧推进量差 < 1.5 个点；给时间戳人为加 **+400ms / −80ms 跳变**，右端位移
必须 < 12px（老实现会跳 ~60px，实测现在 0.7px）。第 9 节专门复现 ③：把时间戳
间隔压到 0.1ms 但帧计数仍按真实速率走，断言一屏点数**纹丝不动**（实测
2045 → 2045，老实现会变成 50000）、曲线铺满 848/847px 而不是缩成 35px。

### 真机上「一卡一卡」的三个专属原因

只跑 TCP 模拟器是看不出这些的。

**① 一批 8 帧共享同一个「收到时刻」**
USB-RS485 转换器的驱动不会一帧一帧把字节交上来，而是每 8~16ms 攒一批再交给应用层
（CH340 / FTDI / CP210x 默认都这样）。同一批的时间戳全挤在一个毫秒里，
画出来是一堆重叠的点，然后隔 16ms 才接上下一小段。

**② 右边界跟着批次跳**
批次之间没有新数据，波形停住不动；下一批一到，猛跳 16ms。

①② 的实测对照（500 Hz 推流、每批 8 帧到达、5s 时间窗）：

| 指标 | 修复前 | 修复后 |
|:--|:--|:--|
| 时间轴偏离（本地时钟 − 延迟 与 右边界的差值） | 平均 59.1ms / 最大 215.5ms / σ=11.2ms | **平均 1.3ms / 最大 2.1ms / σ=0.3ms** |
| 帧时间戳间隔 | σ=0.914ms，**17% 的帧时间戳完全重叠** | **σ=0.031ms，0% 重叠** |

回来量化用 `python _bench_smooth.py`（加 `--legacy` 看修复前的样子）。

**③ 总线上的畸形帧（`AA 55 02 0D 0A` 这种）**
线上偶尔会出现**只有帧头帧尾、没有 24 字节数据段**的短帧：
`AA 55 02 0D 0A`（驱动把帧截断了、线路干扰、或固件在某些状态下发的）。
这种帧本身无害（跳过就行），但早期版本的处理方式很糟：

- 把它当成「长度对不上」→ **丢 1 字节重新同步**，而重同步后解析循环直接 `return` 了，
  一次 recv 只前进 1 个字节，**后面的正常帧全被拖着走**；
- **每个畸形帧记一条 warn 日志** → 每秒几百条，把两个文本框刷爆。

于是总线越脏，界面越卡 —— 而串口助手只做显示，不受影响，所以「别的软件不卡」。

实测（每帧都插一个畸形帧的极端条件，`--short-frames 1`）：

| 指标 | 修复前 | 修复后 | 干净总线（基准） |
|:--|:--|:--|:--|
| 波形帧率 | 23.4 fps | **34.0 fps** | 35.2 fps |
| CPU（单核） | 79% | **62%** | 55% |
| 拆帧重同步 | 6146 次 | **0** | 0 |
| 丢弃乱码字节 | 12290 | **0** | 0 |
| 界面事件积压 | 11 项 | **0 项** | 0 项 |

修法（四层，逐层兜底）：

1. 解析器**整帧识别并跳过**空载荷畸形帧，不再逐字节重同步；
2. `pull_frame()` 增加 `moved` 标志：重同步有进展就继续解析，而不是傻等下一批数据；
3. 同类告警日志**限流到每秒一条**，被压掉的条数合并进下一条（信息不丢）；
4. 界面侧每个刷新周期最多写 8 行日志，超出的只丢显示、队列照样抽干（不会积压）。

### ④ 重绘被「有没有新数据」拖着走 —— 「网络模拟顺、串口卡」的真正根源

这一条最隐蔽，也最致命。旧实现里 `_update_wave()` 是这么写的：

```python
count, samples = cli.take_wave(...)
if not samples:
    return                       # ← 这一 tick 没有新帧，干脆不重绘
self.wave.draw(samples)
```

`take_wave()` 是有状态的：`push_count` 没变就返回空列表。于是**重绘频率被死死
绑在数据到达节奏上**：

- **TCP 回环**：模拟器一帧一帧发，每个刷新周期都有新帧 → 每个 tick 都重绘 →
  满帧率（~35 fps）→ 丝滑；
- **真实串口**：驱动攒批 + 固件主循环发送抖动，批与批之间**没有任何新帧** →
  几十毫秒才重绘一次 → 画面「来一批跳一下、不来就冻住」→ 一卡一卡。

也就是说：**同一段绘图代码，在两种传输下行为根本不一样**。这正是你看到的
「网络模拟的曲线丝滑、串口的曲线很卡」——不是 485 的问题，是上位机把显示
耦合到了到达节奏上。

修法：没新数据也照常重绘（复用上一批样本），时间轴由本地时钟推进，曲线
裁到时间轴右端。实测（330 Hz 推流、60ms 一批到达的恶劣条件）：

| 指标 | 修复前 | 修复后 | 干净 TCP（基准） |
|:--|:--|:--|:--|
| 实际重绘帧率 | 16.6 fps | **34.9 fps** | 35.3 fps |
| 重绘间隔 均值/σ | 60.6 / 13.3 ms | **28.8 / 5.4 ms** | 28.4 / 2.3 ms |

顺带修掉的三处（都和「显示 vs 数据」的关系有关）：

- **曲线尾巴画到时间轴外面**：旧实现一直画到最新样点，比时间轴右端超前一个
  显示延迟，实测超出右边界 ~19px 并被控件边缘硬切。现在裁到时间轴右端，
  曲线端点与右轴的偏差 **-0.3px（σ 0.1px）**。
- **显示延迟改成自适应**：固定 60ms 时，某批数据晚到超过 60ms 就会把右边界
  钉住。现在实测「最新样本年龄」的峰值，延迟 = 峰值 + 15ms（下限 30ms、
  上限 500ms），链路变干净后自动回落。左栏「运行统计 → 显示延迟」能看到它。
  下限从 50ms 降到 30ms 的依据：驱动 Latency Timer 调到 1ms 后实测「接收批
  间隔」9.9ms、样本年龄峰值 ~10ms，再留 50ms 纯属白压 20ms 滞后。
- **串口读取层自己也在加延迟**：`ReadIntervalTimeout` 3ms 配上逐帧连续数据
  （500Hz 时帧间隔 2ms）永远凑不出空隙，只能等 512 字节攒满（≈35ms）才返回。
  改成 1ms / 256 字节，单次读取的额外延迟从 35~50ms 压到 **1~18ms**。

### 排查「卡」：点一下底部「链路体检」

按钮会把判断所需的数字一次性打进日志，并直接给结论：

| 数字 | 读法 |
|:--|:--|
| **帧率** | 远低于 330Hz → 数据端本身就慢：查波特率（EEPROM 里存的，可能被改低过）、固件 `rs485_send_continuous` 的主循环节拍 |
| **接收批间隔 / 每批帧数** | ≥8ms 且每批好几帧 → USB 转串口驱动在按 Latency Timer 攒批，**设备管理器把它从 16ms 改成 1ms 立竿见影**（这是程序改不了的一项） |
| **显示延迟** | 稳定在 30ms 左右 → 链路干净；跟着批节奏涨到 100ms+ → 上面那条的后果 |
| **波形刷新** | 低于设定值 → 瓶颈在本机 CPU/显示端 |

命令行上等价的工具：`python _bench_real.py --secs 14 --sim-port 15020 --diagnose`。

### 固件侧的发送节拍（顺带说明）

`rs485_send_continuous()` 跑在 `main()` 的 `while(1)` 里，且写的是
`g_last_rs485_send_ms = g_tick_ms`（不是 `+= interval`）——主循环一旦慢于
2ms，实际推流率就跟着掉、且**落后了不补**，线上数据本来就是一阵一阵的。
把这一行改成 `g_last_rs485_send_ms += interval;` 可以让节拍自校正；
显示端已经能吃掉这种抖动，改不改都顺，但改了会更跟手。

### 怎么确认总线上到底在发什么帧

自带一个嗅探器，只读不发（加 `--start` 才会先发一条「开始连续」）：

```bat
python y75_sniff.py --port COM28 --baud 460800 --secs 10    :: 真机
python y75_sniff.py --port COM28 --start --secs 10          :: 真机，先让设备开始推流
python y75_sniff.py --tcp 15020 --start --secs 10           :: 不接硬件，连模拟器试试
python y75_sniff.py --port COM28 --all                      :: 逐帧打印原始字节
```

它会给出每个命令码的**期望载荷 vs 实际载荷分布**，以及异常帧的原始字节明细，例如：

```
  帧类型明细：
    0x02  连续推流数据帧  |  期望载荷 24  |  实际 0(618)  24(3094)  |  共 3712 个   ← 有异常
  异常帧明细（共 618 个，显示前 20 个）：
    [  0.205s] AA 55 02 0D 0A    期望 24 字节载荷，实际 0 字节（只有帧头帧尾，没有数据段）
```

界面上「运行统计」也多了一项**「空载荷畸形帧」**：为 0 说明总线干净；
持续增长就是线上真的有短帧（数字会标成橙色提醒）。

附带两条：

- **串口读超时** `ReadIntervalTimeout` 从 30ms 改成 3ms。这个值的语义是「收到第一个字节后
  还愿意等多久下一个字节」，设成 30ms 等于每批数据都在驱动里多躺 30ms 才交上来。
  USB 驱动投递一批是**一次性**的（批内字节间隔 <1ms），3ms 足够收全，白赚 27ms 延迟。
- 波形工具条右侧的**「刷新」**下拉框只影响画面流畅度，不影响数据完整性 ——
  时间轴是按时钟推进的，掉帧只会让画面略跳一下，不会像原来那样越积越偏。

### 想再压一层数据延迟（可选）

转换器驱动自己也能把批量周期调小，不动我们的软件也没问题：

| 芯片 | 做法 |
|:--|:--|
| FTDI (FT232) | 设备管理器 → 端口属性 → 高级 → **Latency Timer** 改 1~2ms |
| CP210x | Silicon Labs 官方 VCP 驱动的「高级」设置里有延迟计时器 |
| CH340/CH341 | 没有公开的调节项，只能靠上位机的等时回放兜住（本版已做） |

另外两处关键修复：

- **`timeBeginPeriod(1)`**：Windows 默认定时器粒度约 15.6ms，Tk 的 `after(33)` 实际会在
  33~49ms 之间乱跳。提到 1ms 之后，实测帧间隔抖动从 **±15ms 降到 ±2.0ms** —— 这才是「顺」的关键。
- **波形缓冲上限 6000 → 20000 帧**：原来 6000 只够 12s@500Hz，把时间窗拉到
  10s / 20s 时左边会空一块。

顺带修掉一个测试缺陷：`test_link.py` 里「错误字节序必然解出 >1e6 的量级」这条断言本身不成立
（传感器值接近 0 时，换序后仍是个极小的数），已改成用已知浮点构造载荷做确定性断言。

### 实测（本机，500 Hz 推流，5s 时间窗，1400×900 窗口）

| 刷新率 | 实际帧率 | 帧间隔均值 | P95 | 抖动(标准差) | 超过 2 倍周期的比例 | CPU(单核) |
|:--|:--|:--|:--|:--|:--|:--|
| 30 fps | 27.6 fps | 34.8 ms | 35.6 ms | ±2.0 ms | 0% | 47% |
| **40 fps（默认）** | 35.7 fps | 27.0 ms | 28.5 ms | ±2.0 ms | 0% | 57% |
| 50 fps | 43.2 fps | 22.3 ms | 25.6 ms | ±2.2 ms | 0% | — |

界面上波形工具条右侧的**「刷新」**下拉框可以实时改（20/25/30/40/50 fps）。
机器慢、或者同时开着别的吃 CPU 的软件时，往下调一档就够了 —— 时间轴是按时钟推进的，
掉帧只会让画面略跳一下，不会像原来那样越积越偏。

### 和 Modbus-TCP 版摆在一起，谁更顺？

`tools/host_pc/_bench_real.py` 直接跑**上位机本体**（完整界面 + 真实收包），逐帧记录
「时间轴右边界」的位置，算出滚动速度的抖动 —— 这才是眼睛看到的「卡/顺」。
`_bench_real_hs.py` 用同一套指标测 `hs_modbus_tcp` 那个 Modbus-TCP 上位机，做对照：

| 指标 | Y75（本版） | Modbus-TCP 版 |
|:--|:--|:--|
| 实际重绘帧率 | **36.7 fps** | 21.3 fps |
| `draw()` 耗时 均值/最大 | **1.4 / 2.5 ms** | 5.5 / 12.9 ms |
| 滚动速度抖动 σ | **1.6 px/s**（均值 174 px/s，≈0.9%） | 7.0 px/s（均值 226 px/s，≈3.1%） |
| 显示延迟（曲线落后最新数据） | **≈60 ms** | ≈0 ms（钉在最新样点上） |
| 宽窗口（4K）开销 | 抽稀上限 1400 点/曲线，封顶 | 800 点/曲线，封顶 |

用法：

```bat
:: 两个终端各起一个模拟器
python y75_simulator.py --port 15020 --rate-hz 330 --burst-ms 12 --quiet
python hs_simulator.py  --port 15502 --rate 500 --quiet

:: 第三个终端分别量
python _bench_real.py    --secs 14 --sim-port 15020
python _bench_real_hs.py --secs 14 --port 15502
```

「运行统计」里新增的**「波形刷新」**一行（`37 fps ±1.0 ms`）就是这两个数的实时版，
不用跑基准也能直接对比 —— 卡不卡不该靠感觉吵。

### 这一版为「跟手」改的三处

1. **实测推流节拍代替假设值**。协议只有 500/1000Hz 两档，但真机的推流跑在固件主循环里
   （`rs485_send_continuous` 用 `g_last = g_tick_ms` 而不是 `+= interval`，主循环慢于 2ms
   时实际推流率就跟着掉），实测常在 300~500Hz。协议层现在每 0.5s 实测一次并做 EWMA
   （`Y75Client._tune_rate`），设备时间轴与真实时间对齐到 **±2ms**（原来是落后 13~20ms）。
   模拟器加 `--rate-hz` 就是用来复现这个条件的。
2. **显示延迟 150ms → 60ms**。原来那 150ms 是给「设备时钟落后」兜底的；节拍实测准了之后
   不需要留那么多，波形跟手程度和 Modbus 版基本一致。
3. **抽稀点数加上限 1400/曲线**。原实现的上限是画布像素宽度，4K 屏把波形拉到 3000px 宽时
   6 条曲线要画近 2 万个点，`draw()` 会从 1.4ms 涨到 20ms+，帧率直接腰斩
   （Modbus 版一直用 800 点硬顶，所以它怎么拉都不卡）。

| `_bench_ui.py` | 波形性能基准（真实 mainloop 下测帧率 / 帧间隔抖动 / CPU） |
| `_bench_smooth.py` | 波形平滑度基准：模拟串口「成批上报」，量时间轴偏离与帧时间戳间隔（`--legacy` 看修复前） |
| `_bench_real.py` / `_bench_real_hs.py` | 跑**上位机本体**量滚动平顺度（右边界位置 → 滚动速度抖动），后者测 Modbus-TCP 版做对照 |

| `build_exe.bat` / `run_host.bat` / `run_simulator.bat` | 打包 / 启动脚本 |

工具链没有硬件时：`python test_link.py --auto`、`python test_gui.py` 会**自己拉起模拟器**。

## 常见问题

| 现象 | 排查 |
|:--|:--|
| 连接后全部命令超时 | ① 串口号选对没 ② 波特率是不是设备当前档位 ③ A/B 有没有接反 ④ DTR/RTS 勾选 ⑤ 设备是否在跑本协议固件 |
| 「读取串口 COMx 失败（拒绝访问）」 | 这个口被别的程序占着（串口助手、另一个上位机实例） |
| 数值全是 0 或乱跳 | 换一下「浮点字节序」下拉框（Y75 固件是标准小端 = DCBA）。注意它**只管数据帧**，矩阵行固定大端 |
| exe 启动报 `No module named 'tkinter'` | 打包用的解释器没带 tkinter，换 `build_exe.bat` 默认那个 |
| 波形不刷新 | 看左下「运行统计」的帧率：没帧率就是没在推流，点「开始连续」 |
| 波形看着卡 / 一顿一顿 | ① 把波形工具条右侧的「刷新」调到 50 或 60 fps（Tk 定时器在 Windows 上约 27ms/帧封顶，再高也不再变快） ② 时间窗别开太大（20s 窗口点数最多）③ 关掉「记录推流帧」勾选 ④ 关掉多余的通道 |
| 点过「停止」再「开始」后，波形只剩右边一小截，而且每停/开一次就少一截 | 老版本会这样：停止的这几秒既没有帧也没有节拍样本，① 帧时间戳的等间隔推算停在断流前（滞后被一路带着走）② 节拍统计窗横跨空洞，量出大好几倍的帧周期，时间戳被推到「未来」，可视窗里就只剩旧数据。本版在起停时把设备时钟和统计窗都重锚、并给推算时钟加了「不许超前本机时间 80ms」的硬夹子（`_break_stream_clock` / `TS_AHEAD`），换新版 exe 即可 |
| 真机上波形「停一下、蹦一下」 | 这是 USB-RS485 驱动成批上报（8~16ms 一批）造成的，本版已用「本地时钟 + 显示延迟」和「等间隔帧时间戳」压掉。若仍有残感：`python _bench_smooth.py --burst-ms 16 --legacy` 与不带 `--legacy` 对比，确认不是环境问题；再按上面「想再压一层数据延迟」调低驱动的 Latency Timer |
| 串口助手里看到 `AA 55 02 0D 0A` | 这是**只有帧头帧尾、没有 24 字节数据段的短帧**（正常数据帧是 29 字节）。本版会整帧跳过并计入「运行统计 → 空载荷畸形帧」，不影响正常数据。想确认线上到底有没有这种帧，跑 `python y75_sniff.py --port COMx` 出报告；若数量持续增长，排查线缆/接地/波特率，或确认固件是否在某些状态下会发短帧 |
| 拖左栏滚动条一卡一卡、面板内容重影/叠字 | 老版本的两个坑：① 滚动域用 `bbox("all")` 算，把**已经移动**的内框位置算了进去 —— 每拖一格滚动域就缩一截（实测 1628→862），一次鼠标事件里内框被搬好几回，Windows 上就留下重影，而且 yview 比例到 1 了内容还差半屏（真底部滚不到）；② `yscrollincrement=20` 把拖动量化成 20px 一跳。本版滚动域只取内框自然尺寸（`_sync_left_scrollregion`）、去掉增量量化，滚轮改为按像素步长。回归检查在 `test_gui.py` 第 6 段 |
